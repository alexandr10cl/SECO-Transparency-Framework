Introduction

The Evaluation Framework for Software Ecosystems Portals (SECO‑TransP) is an open framework designed to evaluate and improve transparency practices in software ecosystem (SECO) portals. It combines structured guidelines, hands-on scenarios, and developer feedback to provide a holistic view of how transparency is perceived and operationalized in real-world SECOs.

By placing developer experience (DX) at the center of the evaluation process, SECO‑TransP helps SECO platform managers, researchers, and ecosystem participants better understand the conditions that foster trust, clarity, and meaningful contributions.

🔍 What does SECO-TransP offer?

  • ✅ 7 Transparency Guidelines (G1-G7), mapped to Common Software Ecosystem Procedures (P1-P7), to DX factors and transparency conditioning factors;
  • 🧪 Evaluation Scenarios that simulate real interactions of developers with portals;
  • 📊 Perception Questionnaire with VAS scale (0-100) to capture subjective experience per KSC;
  • 🛠️ Browser Extension + Evaluation Portal to track scenarios, collect feedback and generate the dashboard;
  • 🏅 Transparency Badges with levels: High • Moderate • Low.

👩‍💻 Who is it for?

  • Researchers seeking a reproducible method to analyze transparency in SECO portals.
  • SECO Platform Managers aiming to identify and enhance transparency practices.
  • Developers interested in contributing to better ecosystems through structured feedback.



Evaluation Workflow

The evaluation using the SECO-TransP framework is conducted in six main steps, starting with the initial setup by the portal manager and ending with the aggregated analysis of the developers' feedback. Below is the complete step-by-step guide:

Step 1: Configure the Evaluation in SECO-TransP

At this stage, a portal manager defines the initial parameters of the evaluation:

  • Provides basic information about the portal to be evaluated.
  • Selects the common software ecosystem procedures to be the focus of the evaluation, such as documentation access, communication channels, governance, etc.
  • Then, the manager saves this initial configuration in the system.

Step 2: Generate Evaluation Code and Link Scenarios

After configuring the evaluation, a portal manager:

  • Generates a unique 7-digit evaluation code.
  • Shares this code with participating developers.
  • SECO-TransP automatically generates evaluation scenarios based on the selected procedures and links them to the code.

Step 3: Developer Access and Profile Questionnaire

Once the developer receives the evaluation code:

  • Accesses the SECO-TransP extension and enters the provided code.
  • Completes a profile questionnaire with information such as education level, work sector, and development experience. This data helps contextualize the evaluation results.

Step 4: Scenario Execution and Quick Feedback

For each assigned scenario:

  • A developer indicates whether they were able to complete the scenario.
  • Optionally, the developer may add a short comment about the scenario.

Step 5: Detailed Evaluation by Success Criteria

After all scenarios of a procedure are completed:

  • A developer answers detailed questions based on the Key Success Criteria (KSCs) of each guideline linked to that procedure.
  • Each question is rated using a Visual Analogue Scale (VAS) from 0 to 100.
  • An optional comment field is provided for qualitative observations.
  • At the end, the developer also provides a general satisfaction rating using a 0-10 slider.

Step 6: Calculation and Interpretation of Results

Based on the developers' responses:

  • Each answer on the VAS is recorded as a numerical value from 0 to 100, where higher values indicate a stronger perception that the criterion was fully met in the portal.
  • The system calculates average scores per criterion, guideline, and procedure.
  • Guidelines are classified as:
    • Fulfilled if the average score is ≥ 75
    • Partially Fulfilled if the average score is between 50 and 74
    • Not Fulfilled if the average score is < 50
  • These classifications are used to generate visual badges and support transparency benchmarking across portals.



Chrome extension guide for testers

Overview

SECO-TransP is a browser extension designed to evaluate the transparency of software ecosystem portals. It guides users through a structured process that includes authentication, session sync, task execution, and experience feedback collection focusing on user interaction and perception.

The extension allows users to:

  • Authenticate using a unique evaluation code
  • Synchronize with UX-tracking
  • Execute guided scenarios for evaluation purposes
  • Log user navigation in real time
  • Provide feedback after each scenario and at the end
  • Submit collected data to a backend server

How to Use

1. Extension Installation

  • Download the latest version of the SECO‑TransP browser extension from the following link: SECO‑TransP Extension
  • Unzip the folder to a location on your computer
  • Go to chrome://extensions/ in Google Chrome
  • Enable Developer mode
  • Click “Load unpacked” and select the folder with your extension files
  • The SECO-TransP icon will appear in the toolbar

2. Authentication

Click on the extension icon to open the authentication screen:

  • Enter the provided 7-digit evaluation code
  • Click “Verify”
  • If the code is valid, you will be directed to the session synchronization step
  • If invalid, an error message will appear

3. Session Synchronization

Before proceeding:

  • Ensure the UX-Tracking system is active
  • Click “Synchronize”
  • If successful, the evaluation overview page will load

4. Evaluation Stages

Step 1: Profile Questionnaire

You will be asked about your academic background, work sector, and experience in software development. These responses help contextualize your feedback.

Step 2: Scenario Execution

Scenarios will be displayed one at a time. For each:

  • Read the scenario title and description
  • Click "Start Scenario"
  • After completing the scenario, choose the option that best indicates whether you achieved its objective:
    • Yes, completely
    • Partially
    • No

Step 3: Scenario Review

After each scenario, you'll write a short comment about your experience and click "Next" to proceed.

Step 4: Process Review

Once all scenarios of a process are completed, a brief questionnaire will be displayed, where each question is answered using a slider scale (0-100) to indicate the extent to which specific objectives were achieved.

Step 5: Final Questionnaire

Finally, you will provide overall feedback about your experience and rate how you felt using the portal using an emoji scale (from 😫 to 🤩).

5. Finishing the Evaluation

  • Click the “Finish Evaluation” button
  • Your responses will be sent automatically to the backend server
  • A success message will confirm completion

What Data Is Collected?

  • Scenario Responses: title, status, timestamps
  • Feedback: text comments, radio/slider selections
  • Navigation: URL history and tab switches
  • Profile Info: academic background, sector, experience
  • Emotion/Satisfaction: final overall rating (e.g., 0-10)

Optional and consent-based: eye-tracking via webcam for gaze estimation.

All data are collected anonymously, stored securely, and restricted to the research team.

Usage Tips

  • If synchronization fails, ensure UX-Tracking is properly started
  • Do not close the popup during the evaluation to prevent data loss



How to Use UX-Tracking

What is UX-Tracking?

UX-Tracking is a tool developed by researchers at the Federal University of Pará (UFPA) that enables detailed tracking of user interactions on web environments. It features multimodal capture, including facial expressions, mouse movements, keyboard input, and audio, allowing for deeper analysis of user experience (UX).

This solution is especially useful for usability studies and research, providing valuable data to understand user behavior and emotions during navigation.

Dashboard Functionality

Purpose

The dashboard is designed to organize and present data in an accessible and analytical way, allowing portal managers to visually analyze evaluation results, identify strengths and weaknesses of the assessed portal, and make data-driven decisions.

Dashboard Structure

The dashboard is divided into four main tabs, each focusing on specific aspects of the evaluation:

1. Overview

Provides a comprehensive summary of the evaluation:

  • Overall evaluation score
  • Scores by SECO dimension (e.g., governance, communication)
  • Scores by Developer Experience (DX) category
  • Participant profile charts: academic background and experience
  • Word cloud with the most cited terms from comments
  • Emotion chart showing developers' overall satisfaction

Transparency Score: Overview

The overall transparency score of the portal is calculated based on the average ratings across all evaluated guidelines. Based on this score, the portal is assigned one of the following transparency levels:

✅ High Transparency: score ≥ 75
🟡 Moderate Transparency: score between 50 and 74
❌ Low Transparency: score < 50

2. Performed Scenarios: Metrics & Badges

This section explains how each scenario metric is computed and which badge is displayed based on the thresholds.

Metric: Time Performance

Definition. Average completion time for a scenario.

How it’s calculated. Mean duration among participants who completed the scenario (failed or abandoned attempts are excluded). If no participant completed the scenario, the time metric is reported as N/A.

Badges. The following badge is displayed based on the average time:

🟢 High Fluency: ≤ 3 min. Scenario completed quickly and smoothly.
🟡 Moderate Fluency: 3-5 min. Scenario completed with acceptable effort.
🟠 Slow Interaction: 5-10 min. Developers needed extra time to find or understand information.
🔴 Cognitive Overload: > 10 min. Scenario took too long; information was unclear or hard to locate.
Examples
  • Average time = 02:06 (mm:ss) → High Fluency
  • Average time = 03:32 (mm:ss) → Moderate Fluency
  • Average time = 06:40 (mm:ss) → Slow Interaction
  • Average time = 11:54 (mm:ss) → Cognitive Overload

Metric: Success Rate

Definition. Percentage of participants who successfully completed the scenario.

How it’s calculated. success rate = (completed / attempted) × 100.

Badges. The following badge is displayed based on the success rate:

🟢 Successful: ≥ 90%. Scenario completed easily and consistently.
🟡 Partially Successful: 70-89%. Most developers completed the scenario, with minor friction.
🟠 Low Success: 50-69%. Several developers struggled to complete the scenario.
🔴 Unsuccessful: < 50%. Most developers could not complete the scenario.
Examples
  • Success rate = 93% → Successful
  • Success rate = 78% → Partially Successful
  • Success rate = 63% → Low Success
  • Success rate = 41% → Unsuccessful

Priority Logic

Each guideline’s priority level is determined by the gap from the target score (75). The larger the gap, the higher the priority for improvement.

  • Gap ≤ 0 → 🟢 Low Priority. Target reached or exceeded.
  • Gap 1-10 → 🟡 Medium Priority. Minor improvement needed.
  • Gap 11-20 → 🟠 High Priority. Significant improvement required.
  • Gap > 20 → 🔴 Critical Priority. Major transparency issue; immediate action recommended.
Examples
  • Guideline score = 78 → Gap = -3 → Low Priority
  • Guideline score = 69 → Gap = 6 → Medium Priority
  • Guideline score = 60 → Gap = 15 → High Priority
  • Guideline score = 48 → Gap = 27 → Critical Priority

3. Hotspots (Heatmaps)

When multimodal tracking via UX-Tracking is enabled, this section presents heatmaps per scenario:

  • Visualization of the most clicked or hovered areas
  • Helps identify zones of interest, confusion, or abandonment during scenario execution

This visual layer complements the quantitative data with behavioral insights.

4. Guidelines Score

The Guidelines Score section displays the evaluation results based on each guideline’s Key Success Criteria (KSCs). Developer responses on a VAS (0-100) are translated into scores and statuses.

Each evaluated guideline is presented with:

Evaluated Guidelines

A complete list of the guidelines selected for assessment during the evaluation process.

Average Score

The system calculates an average score for each guideline based on developer responses to its associated KSC. Each response is given on a VAS from 0 to 100, where higher values indicate a stronger perception that the criterion was fully met in the portal. The average is computed across all KSC linked to the guideline and is used to determine the corresponding fulfillment badge classification.

Status Classification

According to the average score, each guideline is classified as:

Fulfilled: 75 or higher
Partially Fulfilled: between 50 and 74
Not Fulfilled: below 50

KSC Visualization

Each guideline includes a breakdown of its KSC, showing individual scores and status indicators. This helps identify precisely where the portal meets or falls short on transparency expectations.

Glossary of Terms

This glossary provides definitions for key terms used throughout the SECO‑TransP framework.

Conditioning Factors for Transparency
Elements, characteristics, or actions that are necessary but not sufficient for the transparency of software ecosystems. A recent study identified and analyzed these factors through a systematic mapping and field study, structuring them around themes like access to information, communication channels, and requirements engineering (Zacarias et al., 2024).
Developer Experience
A broad concept that captures how developers feel about, think about, and value their interactions with tools, platforms, processes, and documentation. It encompasses emotional, cognitive, and practical aspects that influence developer satisfaction, efficiency, and motivation.
Developer Experience Factor
A specific circumstance, condition, or influence that affects how developers perceive and experience their interactions within a software ecosystem. These factors can be technical, cognitive, social, or emotional, and collectively shape the overall developer experience. A recent study identified 27 such factors, highlighting especially the influence of “financial costs for using the platform”, “desired technical resources for development”, “low barriers to entry into the application market”, and “more financial gains”, as key determinants for third‑party developers when deciding to adopt and continue contributing to a SECO (Zacarias et al., 2025).
Evaluation Scenario
A practical scenario performed by developers in the portal to simulate real interactions and assess the level of transparency in a specific procedure.
Key Success Criterion
A concrete indicator used to evaluate whether a transparency guideline is effectively fulfilled from a developer's point of view.
Software Ecosystem
A set of actors that function as a unit and their relationships and interactions within a distributed market of software and services. These relationships are typically centered around a common technological platform, allowing the exchange of information, resources, and artifacts.
Software Ecosystem Portal
A web-based interface that provides access to artifacts, tools, documentation, and services offered by a common technological platform within a software ecosystem.
Transparency
A condition in which information about capabilities, priorities, and behaviors is openly available, enabling informed decision‑making by stakeholders and reducing inefficiencies caused by information asymmetry.
Transparency Badge
A visual indicator assigned to a guideline based on evaluation scores. The three levels are: High Transparency (≥ 75), Moderate Transparency (50-74), and Low Transparency (< 50).
Transparency Guideline
A recommended practice aimed at increasing visibility, clarity, and fairness in specific areas of the SECO portal (e.g., source code access, governance, contribution policies).
VAS (Visual Analogue Scale)
A type of measurement scale where developers indicate their perception by selecting a position along a continuous line, typically from 0 to 100.
